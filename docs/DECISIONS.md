# Engineering Decision Log

This is a running log of the non-obvious engineering calls made on this project — not just *what* was built, but *why*, what else was considered, and what tradeoffs were accepted along the way. Inline code comments explain a specific function's local reasoning; this file is the bigger picture, meant to be readable end-to-end without the code open.

It exists for two reasons: to keep a real record while the project is being actively developed with AI-assisted pairing, and to serve as a reference for explaining the project's design decisions to a technical audience (interviews, a portfolio walkthrough, a talk). Entries are in chronological order. Each one follows roughly the same shape: **Context** (what problem existed), **Decision** (what was actually done), **Why**, **Alternatives considered**, and **Consequences / left open** (the honest tradeoffs and what's deliberately deferred).

---

## Auto-assignment via sort order, not a routing algorithm

**Context:** Shoppers need orders assigned to them somehow. A real fulfillment platform (Whole Foods/Amazon-style) runs this through a dedicated routing/dispatch system — proximity, shopper load, order age, all weighed together, often as its own service.

**Decision:** Orders are assigned by a simple deterministic rule: when a shopper flips their status to Available, the app queries all `pending` unassigned orders sorted by `scheduledReadyTime` ascending, and hands them the single most time-urgent one (`getNextOrderForAssignment` in `orderService.ts`). No weighting, no scoring, no server-side function.

**Why:** This is a solo portfolio project, not a production dispatch system — the goal was to demonstrate a coherent, correct assignment *mechanism* (query, sort, assign, persist) rather than reimplement a logistics-routing algorithm that would take the scope far beyond what a mobile app + BaaS backend needs to prove. Sorting by `scheduledReadyTime` also happens to be the one signal that matters most for a grocery pickup app specifically: whichever order is due soonest should go out the door first.

**Alternatives considered:** A serverless Appwrite Function that runs assignment logic server-side (more realistic architecture, matches the README's stated "Functions (Node.js serverless)" tech goal) was considered but deferred — the client-side version proves the same data flow with far less infrastructure to stand up first.

**Consequences / left open:** This is explicitly flagged in the README as a simplification ("a simple client-side flag today, not yet a ranking/routing algorithm or serverless function"). It also means assignment only happens at the moment a shopper *becomes* available — an order placed while a shopper is already active and idle-available doesn't get pushed to anyone until the next status change or manual pull. That gap is directly what motivated the rush-order interrupt discussion below.

## Appwrite schema drift, and how it was diagnosed

**Context:** The Appwrite Cloud collections were hand-created through the console early on, and drifted from what the app code actually read/wrote — `shopperId` vs. the real attribute `shopperID`, `lastActiveTimestamp` vs. `lastActiveTimeStamp`, missing `Create`/`Delete` permissions. Shopper registration was failing, and the client SDK's own error messages were actively misleading: a failed *rollback* delete (masked by a missing `Delete` permission) surfaced as "not authorized," hiding the real attribute-casing bug underneath it.

**Decision:** Rather than iterate error-by-error through the Appwrite console, a server-side API key (scoped to Databases read/write, Auth users read/write) was added to `.env` for local debugging, used to pull each collection's *actual* attribute list via the REST API (`GET /v1/databases/{db}/collections/{id}`) and diff it directly against every `createDocument`/`updateDocument`/`Query.equal` call in the code.

**Why:** Debugging a schema mismatch by reading error messages one at a time is slow and, in this case, actively misleading (the rollback masking bug). Diffing the ground-truth schema against every call site in one pass found all four drift points (casing on two attributes, two permission gaps) in a single debugging session instead of four separate ones.

**Alternatives considered:** Fixing the *schema* to match the code (renaming the Appwrite attributes) was the other direction this could have gone. The code was changed instead, since the console-configured schema was the "source of truth" already in use and changing it risked breaking anything else already pointed at it.

**Consequences / left open:** This also caught a real, independent bug in passing: `getShopperStatus()` querying a nonexistent field (`shopperId`) silently returned zero results instead of throwing — meaning it would have quietly broken availability toggling and order auto-assignment for every registered shopper without ever raising an error. Silent empty-result failures like this are worth specifically watching for in Appwrite (or any query-based) code, since they don't announce themselves. **The debug API key is dev-only** — it's deliberately never shipped in the client app; the client SDK's inability to do things like delete Auth accounts is an intentional Appwrite platform boundary, not a workaround target.

## Pickup time slots scoped to pickup only, not delivery

**Context:** Checkout hardcoded every order's `scheduledReadyTime` to "30 minutes from now," with no way for a customer to actually choose a pickup time.

**Decision:** Added a time-slot picker (`TimeSlotSelector.tsx`), but scoped its rendering and validation strictly to `fulfillmentType === 'pickup'`. Delivery orders were deliberately left on the old hardcoded default.

**Why:** The actual ask was about picking up an order — there was no delivery-dispatch UX requirement in scope, and guessing at one (a delivery window picker, driver ETA logic, etc.) would have been solving a problem nobody raised. Scoping tightly to the real request kept the change small and correct instead of speculatively building out an adjacent feature.

**Alternatives considered:** A single generic "scheduled time" picker for both fulfillment types was considered and rejected for the same reason — it would've had to either fake delivery-window semantics or leave half its options meaningless for a delivery order.

**Consequences / left open:** Delivery orders still have no real scheduling story. That's a known, intentional gap, not an oversight.

## Rush orders: hourly slots + reusing an existing field over adding a new one

**Context:** Following on from the time-slot feature above: normal pickup slots were on a 30-minute grid, and there was no way to get an order ready faster than the next slot. The ask was for pickup slots to land on the hour, plus a "Rush Order" option that bypasses slot selection entirely and targets 30 minutes out instead.

**Decision:** Changed the normal slot interval from 30 to 60 minutes, added a `RushOrderToggle` component and `getRushReadyTime()` helper, and — instead of adding a new schema attribute to flag a rush order — reused the `priority` field that already existed on the Order schema (visible in the README's Orders Collection table) but was never actually set by any code path. `priority: 1` now means "rush," `0` means normal.

**Why:** Adding a new boolean attribute (e.g. `isRush`) would have meant another Appwrite console change plus another field to keep the type, the write path, and any future read paths in sync — for information that `priority` already existed to carry and wasn't carrying. Since order assignment already sorts by `scheduledReadyTime` ascending, a rush order's soonest-in-the-queue ready time means it naturally sorts to the front of assignment with zero changes to the assignment logic itself — the existing mechanism from the decision above "just worked" for a new case it wasn't originally written for.

**Alternatives considered:** A new `isRush` boolean field, and a special-cased branch in the assignment query to prioritize rush orders explicitly, were both considered and rejected as unnecessary — see Why.

**Consequences / left open:** `priority` is now implicitly a two-state (0/1) rush flag rather than a general-purpose priority scale, which is a semantic narrowing worth knowing about if a future feature wants "priority" to mean something more granular. Verified end-to-end in the Android emulator, including confirming the placed order's Appwrite document had `priority: 1` and a `scheduledReadyTime` exactly 30 minutes after `orderDate`.

## Releasing a shopper's order when they go unavailable

**Context:** A shopper toggling their status to Unavailable while actively working an order left that order permanently stuck `assigned` to them — it never returned to the pending queue, so it would just sit there indefinitely, invisible to every other shopper.

**Decision:** `updateShopperAvailability` now branches on becoming-available vs. becoming-unavailable. Going unavailable while holding an order calls a new `unassignOrder()` (resets `shopperID` to empty, `status` back to `pending`, `autoAssigned` to `false`) and then `reassignIfMostUrgent()` immediately checks whether that now-freed order is the single most urgent thing in the queue — if so, it's hitched straight to the next idle shopper instead of waiting for someone to notice it later.

**Why:** An order silently going stale because its shopper stepped away is a worse failure mode than briefly having no shopper on it — it should always be recoverable by falling back into the same pool every other pending order lives in.

**Alternatives considered:** Leaving the order `assigned` but flagging the shopper as unavailable (so a manager/dashboard could manually reassign) was considered and rejected — there's no manager-facing reassignment UI in this app, so that would have created an order with no path back to being worked at all.

**Consequences / left open:** `reassignIfMostUrgent` only ever acts on an order that has *already* been released back to `pending` — it does not, and was never designed to, take an order away from a *different* shopper who's actively working it. That distinction is the crux of the rush-order interrupt gap discussed below.

## Pull-based data, not realtime — a scope boundary, not an oversight

**Context:** The README's original tech goals list Appwrite Realtime (WebSocket subscriptions) as a planned technical highlight. As built so far, nothing in the app subscribes to anything — `ShopperDashboardScreen` refetches its status/task data on `useFocusEffect` (i.e., whenever the screen regains focus), and that's the only refresh mechanism anywhere.

**Decision (so far, implicit through omission):** Ship the pull-based version first — fetch-on-focus, fetch-on-manual-refresh — and treat realtime subscriptions as a distinct follow-up phase rather than a blocking requirement for every other feature.

**Why:** Pull-on-focus is enough to prove every other piece of the data flow (auth, CRUD against Appwrite, order lifecycle, assignment) end-to-end without also standing up and debugging a WebSocket subscription layer at the same time. It's a smaller, independently-verifiable slice.

**Alternatives considered:** None seriously — this was more a sequencing choice than a considered tradeoff at the time each feature was built. It's called out explicitly here because it stopped being a free simplification the moment a *live* interrupt notification was requested (see next section): a shopper mid-shop won't see anything change on their screen until they navigate away and back, no matter what the backend does, until realtime is actually wired in.

**Consequences / left open:** This is the single biggest piece of infrastructure the app is currently missing relative to its own stated goals. Concretely blocks: live order-status updates for customers, and any kind of push notification to a shopper (new assignment, interruption, etc.) without them manually refreshing.

## Rush-order shopper interrupt: identified as a gap (built below)

**Context:** Testing the rush-order feature live (two Android emulators running a customer and a shopper session side by side) surfaced that placing a rush order while a shopper is already mid-shop on a different order does *nothing visible* — no notification, no reassignment, nothing. Real gig-fulfillment apps (Whole Foods/Amazon Flex-style) both notify a shopper immediately when a new order is assigned (with accept/decline), and can interrupt an in-progress order for something more urgent.

**Findings from auditing the existing code:** Two things suggested this was *intended* to exist eventually but never got built: the Appwrite `orders` collection already has `interruptedAt`/`interruptReason` attributes defined (visible in the README's schema table), but they're `null` on every order and referenced by zero lines of app code — a schema anticipated ahead of the feature that implements it. Separately, the reassignment logic added for the "shopper goes unavailable" fix above only ever operates on an order already back in the `pending` queue — by design, it never reaches into a *different* shopper's active order.

**Decision:** Not yet built. Documented as two separable features instead of one: (1) an accept/decline confirmation modal shown when a shopper goes Available and an order auto-assigns (self-contained, no new infrastructure — the order is already returned synchronously today, it's just never surfaced to the user), and (2) true mid-shop interruption for rush orders, which needs interrupt-decision logic (who gets interrupted and when), the realtime layer from the section above (otherwise "interrupted" just means "silently different next time you refresh"), and the actual notification UI (`react-native-paper`'s `Dialog`/`Portal`, already an unused dependency, is the natural building block over reaching for a new library).

**Why documented before implemented:** Given how much this touches — schema, backend assignment logic, a whole missing realtime layer, and new UI — going in with an explicit plan matters more here than for most of the smaller fixes above, hence stopping to write this down and get alignment before writing any code.

**Consequences / left open:** This is the current known frontier of the project. Whichever of the two sub-features gets built first should get its own entry here once it exists.

**Update:** Both sub-features were built next - see "Accept/decline on new assignment" and "Rush-order interrupt: decision logic, polling, and notification UI" below.

## Dual-emulator setup for live cross-role testing

**Context:** Verifying "does a shopper see X happen when a customer does Y" requires watching both roles' screens change in real time, which a single emulator (and a single logged-in session) can't do.

**Decision:** Run two independent Android emulator instances side by side — a second AVD (`Shopper_Phone`) cloned from the primary one's config, given its own fresh userdata so it can hold a separate logged-in session, sharing the same Metro bundler and the same real Appwrite backend as the primary emulator.

**Why:** This is the only way to actually *observe* a cross-role live-update bug or gap (like the rush-order interrupt gap above) rather than infer it from reading code — the blank-screen-until-refresh behavior on the shopper side was directly visible this way, side by side with the customer's action that should have (eventually) caused it.

**Alternatives considered:** A single emulator with logout/login switching between customer and shopper accounts was the fallback, but it can't show simultaneity — by the time you'd switched accounts to check the shopper's screen, you'd have lost the ability to tell whether an update was "live" versus "just refreshed."

**Consequences / left open:** Two emulator instances is noticeably heavier on the dev machine (RAM/CPU) than one — fine on the current 12-core/30GB machine, but worth knowing as a cost if this pattern gets reused for a machine with less headroom.

## Accept/decline on new assignment

**Context:** When a shopper toggled to Available and an order auto-assigned, it happened silently - the dashboard's current task just changed underneath them with no confirmation step, unlike the accept/decline pattern real gig-fulfillment apps use.

**Decision:** Added `NewAssignmentModal`, shown right after `updateShopperAvailability` returns a newly auto-assigned order (in `ShopperDashboardScreen.handleStatusChange`) instead of immediately setting it as the current task. Accept promotes it to the current task as before. Decline calls `updateShopperAvailability(shopperId, false)` a second time - no new backend logic needed, since by that point the shopper's status doc already has `currentOrderId` set, so the existing "going unavailable while working an order" branch (built for the earlier unassign fix) releases it back to `pending` and offers it to the next idle shopper, exactly as if the shopper had gone unavailable mid-task on their own.

**Why reuse `updateShopperAvailability` for decline instead of a dedicated decline function?** The state after auto-assign-then-decline is identical to the state after go-available-then-go-unavailable-mid-task - same order, same shopper, same "release it" outcome. Writing a second code path for the same state transition would just be two ways to do one thing.

**Alternatives considered:** A `react-native-paper` `Dialog`/`Portal` was considered for the modal itself, since the library's already a dependency, but set aside in favor of the same bare `Modal` + `Pressable`-backdrop pattern already proven in this codebase (`ShopperStatusDropdown`) - untested library components didn't need to be introduced for something the existing pattern already handles well. One correction carried over from that component: its inner content wasn't actually wrapped in its own `Pressable` to stop touch propagation, despite a comment claiming it was - fixed properly in the new component.

**Consequences / left open:** None significant - this is fully self-contained, no schema or realtime changes, verified end-to-end in the emulator (toggle Available, modal appears with correct order #/time; Decline confirmed via Appwrite REST to release the order back to `pending`; Accept confirmed to populate the current task).

## Rush-order interrupt: decision logic, polling, and notification UI

**Context:** Continuing directly from the gap identified above - build the actual interrupt behavior: when a rush order is placed and every shopper is already busy, take the least-urgent in-progress order from whoever has it and hand them the rush order instead, then tell them live.

**Decision, in three parts:**

1. **Schema/types:** Added `interruptedAt`/`interruptReason` to the `Order` TypeScript type (the Appwrite attributes already existed, unused) and a new `interruptOrder()` in `orderService.ts` - same shape as the existing `unassignOrder()`, plus the two new fields. Kept as a separate function rather than an optional flag on `unassignOrder`, since the two model different things: a shopper voluntarily stepping away vs. an order being taken from them.

2. **Decision logic:** New `handleRushOrderPlacement()` in `shopperStatusService.ts`, triggered from `CheckoutScreen` right after order creation, scoped to `priority === 1` only (normal orders keep their existing assign-on-availability-toggle behavior unchanged - broadening that further wasn't asked for). Tries an idle shopper first (reusing `getNextAvailableShopper`, no interruption needed); if everyone's busy, a new `getInterruptCandidateShopper()` finds whoever's current order has the furthest-out `scheduledReadyTime` - the same signal the rest of the assignment logic already sorts by, reused here rather than inventing a second heuristic (e.g. shopping progress) for a first version.

3. **Live notification:** New `ShopperAssignmentContext`, polling `getShopperStatus` every 8 seconds while a shopper is anywhere in the shopper navigation stack (mounted once in `AppNavigator.tsx`, wrapping the whole `ShopperStack.Navigator`, not per-screen). True Appwrite Realtime was investigated and set aside for now - this SDK version's React Native behavior here is unverified territory (undocumented database-scoped channel format, an unguarded `window.localStorage` access in the Realtime service's connection handler that likely isn't a global in this RN runtime). Polling reuses an already-proven fetch with zero new unknowns, at the cost of latency instead of instant push.

**A real bug caught during live verification:** the first version's interrupt reason was a dynamic string (`Interrupted for rush order ${orderId}`), which failed at write time - `interruptReason` is capped at 40 characters on the Appwrite schema, and the dynamic string was well over that. Caught immediately via a live end-to-end test (an `AppwriteException` in `adb logcat`, not a silent failure) and fixed to a short fixed string. Worth calling out because it's exactly the kind of thing that only surfaces by actually running the flow against the real schema, not from reading the code or type-checking alone - `interruptReason: string` in TypeScript says nothing about a server-side length cap.

**Verified end-to-end (2026-08-17):** two busy shoppers set up across the dual-emulator setup, a rush order placed while both were mid-order; the interrupt logic correctly picked the shopper with the furthest-out `scheduledReadyTime`, released their order (confirmed via Appwrite REST: `status: pending`, `interruptedAt`/`interruptReason` set), assigned the rush order to them instead, and the polling-driven `OrderInterruptedModal` appeared on their device within the poll window with the correct order details.

**Consequences / left open:** If the shopper is actively viewing `TaskDetailScreen` for the exact order that gets interrupted, that screen doesn't auto-refresh or auto-navigate away (a pre-existing limitation of that screen - it fetches once on mount - not something this feature introduces). Realtime remains a documented future upgrade over polling, should the up-to-8-second latency ever matter more than the integration risk did at the time this was built.

## Phase 4 core loop: claim → shop → complete

**Context:** A Phase 4 shopper-features spec, originally written in a browser session before this project moved to Claude Code CLI, was pasted in for a gap audit. Auditing found 4.1 (dashboard) done, 4.2 (order acceptance) partially done (auto-assignment accept/decline existed; manually claiming an order from the available-tasks list did not), 4.3 (shopping workflow) and 4.5 (completion) entirely unbuilt (`updatePickedItems()` existed with zero callers), 4.4 (arrivals) done on the customer side only, and 4.6 (emergency stop) already functionally covered by the existing "toggle Unavailable while working an order" release-and-reassign behavior (see above). The spec's suggested architecture (a `/hooks` directory, Appwrite Realtime subscriptions) was explicitly not followed - it conflicts with the "Pull-based data, not realtime" decision above.

**Decision:** Built the core loop only - claim an order, work a checklist (found/out-of-stock/substitute with customer approval), complete it - scoped down from the full spec by explicit user choice. Shopper-side arrivals and a dedicated in-shopping-screen emergency-stop action were deferred to a later pass.

**Schema:** Added one new optional `Order` attribute, `itemIssues` (string, 1000 chars, default `""`), via the Appwrite REST API using the debug `APPWRITE_API_KEY` already in `.env` (previously used read-only for schema inspection, per the "Appwrite schema drift" entry above - this is its first write use, with explicit user go-ahead beforehand). Encodes out-of-stock markers and substitution proposals/approval state per item, compact-string style like the existing `items`/`pickedItems` fields: `productId:oos` or `productId:sub:subProductId:pending|approved|rejected`. Parse/format helpers live in the new `src/utils/orderItems.ts`.

**Why one field instead of a new collection?** The existing `OrderMessages` collection (`messageID, orderID, senderID, receiverID, messageContent, sentDateTime, isRead`) was inspected live and found to be a generic chat shape with no status/approval fields - encoding structured substitution state into it would have meant JSON-stuffing `messageContent`, which isn't simpler than one purpose-built compact-string field following the pattern already established by `items`/`pickedItems`.

**Substitution approval, without realtime:** The shopper's `ShoppingScreen` polls the order every 8 seconds (same interval as `ShopperAssignmentContext`) only while a proposed substitution is `pending`. The customer's `OrderDetailScreen` polls the same way, but scoped to `order.status === 'shopping'` (the only window a new proposal could appear in), reusing its existing `loadOrder()`. Both are local `useEffect`/`setInterval` polls, not a new global context - each only matters while its own screen is open.

**Reuse over duplication:** `updateShopperAvailability`'s "becoming available with no order → auto-assign the next pending order" logic was extracted into a shared `autoAssignNextOrderTo()` in `shopperStatusService.ts`, since `OrderCompletionScreen` needed the identical sequence after freeing a shopper. `assignOrderToShopper()` in `orderService.ts` gained a third `autoAssigned` parameter (default `true`, preserving every existing caller) so the new manual-claim path from `TaskDetailScreen` could pass `false` without a separate function.

**Verified end-to-end (2026-08-18, dual-emulator):** start shopping → propose a substitute → customer approves via the 8s poll → shopper's screen picks up the approval via its own 8s poll → mark ready for pickup → shopper freed and the next pending order auto-assigned, confirmed live on the dashboard. Also verified the claim-gating fix below by attempting to open a second pending order while already mid-task and confirming no claim action was offered.

**Three real, pre-existing bugs surfaced by running the actual flow (not caught by `tsc`/`eslint`, exactly the kind DECISIONS.md keeps flagging as only found live):**

1. **`Query.search('name', ...)` had no fulltext index.** `productService.searchProducts()` - used by the customer home screen's search bar since Phase 3, and now by the new `SubstitutionPickerModal` - was calling `Query.search` against a `Products` collection with zero indexes defined. Every search silently failed with `AppwriteException: Searching by attribute "name" requires a fulltext index`, console-logged but never surfaced to a human before now. Fixed by adding a `fulltext` index on `Products.name` via the API key. This means customer product search was very likely broken in production since Phase 3 shipped, unrelated to Phase 4's changes - just never previously exercised by someone watching the console.

2. **`ready_for_pickup` was never added to the `Order.status` enum on Appwrite**, even though the TypeScript `OrderStatus` type and the customer-facing UI (`OrderTimeline`, `OrderStatusBadge`) have included it since Phase 3's pickup/arrival work. No order could ever actually reach that status - `completeOrder()` failed with `Invalid document structure` on first live attempt. Fixed by widening the enum's `elements` to include it (kept `default: 'pending'`, `required: false` unchanged). Confirmed live afterward.

3. **Claiming an order didn't check whether the shopper already had one in flight.** `TaskDetailScreen`'s claim action offered "Claim & Start Shopping" on any pending order regardless of the shopper's own `ShopperStatus.currentOrderId` - claiming a second order while mid-task on a first would silently orphan the first (its `shopperID` stays set, but nothing points `ShopperStatus.currentOrderId` at it any more, so it's unreachable by the release-back-to-queue path). Same failure mode the "releasing a shopper's order when they go unavailable" fix (above) exists to prevent, just reachable through a different door. Fixed by fetching the shopper's own status on `TaskDetailScreen` mount and gating the `claim` branch on `!shopperActiveOrderId`, mirroring the exact guard `updateShopperAvailability` already uses (`isAvailable && !previousOrderId`). Verified live: with a task already assigned, opening a different pending order's detail screen now shows no claim action.

## Manual order swap + non-blocking "more urgent order" toast

**Context:** The claim-gating fix above solved the orphaning bug but created a new gap: a shopper mid-task on a low-urgency order had no way to switch onto a newly-arrived, more time-sensitive order without first abandoning their current one via the status dropdown (losing the direct navigation flow) - and had no way to even find out such an order existed short of manually re-checking Available Tasks. Concrete scenario given: shopper starts a 2pm-due order at 9am; an 11am-due order arrives while they're mid-shop; nothing on screen reflects that.

**Decision, in two parts:**

1. **Manual swap.** `TaskDetailScreen`'s claim-gate now offers a third action, `swap`, when viewing a different pending order while already mid-task: confirms via `Alert.alert` (showing the current order's short id and due time), then `swapCurrentOrder()` (new, `shopperStatusService.ts`) claims the new order *before* releasing the old one (so a failed claim leaves the shopper with their original order intact, not stranded with neither), then releases the old order via the existing `unassignOrder`, then calls the newly-exported `reassignIfMostUrgent` (previously private, used only by the go-unavailable path) so the released order gets an immediate hand-off to another idle shopper if it's now the single most urgent thing pending - same behavior as every other release path in this app, reused rather than reinvented.

2. **Non-blocking urgent-order toast.** Extended `ShopperAssignmentContext`'s existing 8s poll (see "Rush-order interrupt" above) to also compare the pending queue's single most urgent order (`getNextOrderForAssignment`, already sorted ascending by `scheduledReadyTime`) against the shopper's own current order's due time, only while `assigned`/`shopping`. If the queue has something more urgent, a `Snackbar` (`UrgentOrderToast`, new) shows a dismissable, auto-expiring notice - deliberately not `OrderInterruptedModal`'s blocking treatment, since nothing happened to *this* shopper's order, they just might not know something more urgent is sitting unclaimed. A `lastNotifiedUrgentOrderIdRef` prevents re-notifying for the same still-unclaimed candidate on every subsequent tick, reset whenever the shopper's own current order changes.

**Two more bugs found live while testing this (neither introduced by this feature, both reproduced by it):**

- **Order short-id display was inconsistent.** `ShopperDashboardScreen`'s `generateShortOrderId` and `OrderInterruptedModal` both truncated by the *first* 8 characters (`substring(0, 8)`), while every other screen (`TaskDetailScreen`, the customer `OrderDetailScreen`) truncates by the *last* 8 (`slice(-8)`). The same order showed two different "short ids" depending which screen you were on - caught directly when the swap confirmation dialog's order id didn't match what the dashboard had just shown for the same order. Fixed both to `slice(-8)` to match the majority convention.
- **`interruptedAt` was never cleared on reassignment, causing a false "Order Reassigned" modal.** An order genuinely interrupted for a rush order in an earlier session kept that `interruptedAt` timestamp forever. When it later got auto-assigned, then released again for an unrelated reason (this session's swap), `ShopperAssignmentContext`'s polling only checks "is `interruptedAt` set", not "was this order *just* interrupted in this transition" - so it fired the interrupt modal off stale history. Fixed at the root: `assignOrderToShopper()` (`orderService.ts`) now clears `interruptedAt`/`interruptReason` on every fresh assignment, regardless of which of its several callers (auto-assignment, manual claim, swap) does the assigning - the moment an order is freshly assigned is the one point where any prior interrupt is unambiguously resolved.

**Verified end-to-end (2026-08-18, dual-emulator):** swap confirmed via the app (correct confirmation dialog, correct navigation into the new order) and independently via direct Appwrite REST reads (released order back to `pending`/unassigned, new order `shopping` with the right `shopperID`, `ShopperStatus.currentOrderId` updated). Toast confirmed visually rendering with the correct message and a working Dismiss action.

**Consequences / left open:** During rapid dev-loop testing (repeated `am force-stop` + relaunch cycles within seconds of each other, not a realistic usage pattern), the toast's first firing after a fresh app launch showed inconsistent timing - sometimes on the first eligible poll tick, sometimes not for several minutes, despite the underlying comparison logic (traced with temporary debug logging) evaluating correctly and identically every time it ran. Root cause not conclusively identified; suspected Metro/Hermes bundle-cache interaction with unusually frequent cold-start cycles rather than an app logic bug, since a real shopper session mounts this provider once and polls continuously rather than restarting every few seconds. Worth a closer look if it's ever observed to be slow on a real device across a normal session.

## Back button restored on Shopping/OrderCompletion; current-task tap skips TaskDetail

**Context:** `Shopping` and `OrderCompletion` were built with `headerBackVisible: false`, reasoned at the time as preventing a shopper from accidentally abandoning mid-shop progress via the header - "go Unavailable" via the status dropdown was meant to be the only intentional exit. In practice this left the shopper with no way off either screen at all except finishing the checklist (`Shopping`) or completing the order (`OrderCompletion`) - the status dropdown lives on the Home screen, which was exactly the screen this made unreachable.

**Decision:** Removed the `headerBackVisible: false` override from both screens in `AppNavigator.tsx`, restoring React Navigation's default back button everywhere in the shopper stack except `ShopperHome` itself (which has its own custom header by design). Separately, `ShopperDashboardScreen`'s current-task card now navigates straight into `Shopping` instead of routing through `TaskDetailScreen` first - that intermediate stop only ever offered a single "Continue Shopping"/"Start Shopping" button for an order the shopper already owned, so it was pure friction. An order still in `assigned` status gets `startShopping()` called first (the same transition `TaskDetail`'s "Start Shopping" action used to perform) before navigating in, so the order's status field stays accurate.

**Why the original safety concern didn't hold up:** Checked `ShoppingScreen`'s actual persistence path before making this change - `persistPicked`/`persistIssues` write to the `Order` document (`updatePickedItems`/`updateItemIssues`) on every Found/quantity/substitute action, optimistically updating local state and reverting only on a failed Appwrite write. Progress is durable per-action, not batched at a final submit step. With that confirmed, blocking all navigation was paying a real cost (a shopper stuck on the screen with no way to check anything else, or to back out of an accidental tap) to guard against a data-loss scenario that doesn't exist - the order document already reflects whatever was true at the moment of navigating away, exactly as if the shopper had returned to Home and reopened the same task later.

**Alternatives considered:** A confirmation dialog on back-press (keeping some friction, in the spirit of the original reasoning) was considered and rejected - once the premise (unsaved progress at risk) was verified false, a warning about a risk that can't occur would just be friction with no corresponding protection.

**Consequences / left open:** None significant - back navigation mid-shop is exactly as safe as the existing Home → reopen-task path already was. `AvailableTasks`, `DropOffs`, `CustomerCheckIns`, `TaskDetail`, and `ShopperSettings` were unaffected - they already had default back buttons and were never part of the original restriction.

## Urgent-order toast fired for orders already in the queue, not just new arrivals

**Context:** The "Manual order swap + non-blocking toast" entry above documented `lastNotifiedUrgentOrderIdRef` resetting to `null` whenever the shopper's `currentOrderId` changed (swap, claim, auto-assign) as the mechanism for a "fresh comparison baseline" on the new task. Live use surfaced the actual effect of that reset: swapping into an order that itself wasn't the single most urgent thing pending - i.e., other orders already sitting in the queue, visible before the swap, were more time-sensitive than the one just chosen - caused the toast to fire on the very next poll (within 8 seconds), even though nothing new had arrived. The `null` reset meant the first post-change comparison had no baseline to compare against, so it treated the pre-existing queue state as a brand-new discovery.

**Decision:** Replaced the `null` reset with a second ref, `lastUrgentCheckOrderIdRef`, tracking which of the shopper's own orders the notification baseline was last established for. Whenever `currentOrderId` changes, the first urgent-check poll against the new order silently records whatever's currently most-urgent-pending as the baseline (no toast) instead of comparing it as new. Only a candidate appearing on a *later* poll - genuinely arriving after that baseline was set - fires the toast.

**Why:** The toast exists to tell a shopper about an order that showed up after they committed to their current task, not to relitigate queue state they either already had visible (browsing Available Tasks immediately before a manual swap) or had no opportunity to see yet (a first-ever claim). Firing on pre-existing orders produced exactly the failure mode this kind of notification is supposed to prevent: noise indistinguishable from a genuine "something changed" signal, undermining the reason the toast was built in the first place.

**Alternatives considered:** None seriously weighed - once the reset-to-`null` was identified as the root cause, baselining per-order was the direct fix; no other approach was considered.

**Consequences / left open:** The 8-second poll latency and dev-loop cold-start timing flakiness noted in the swap/toast entry above are unchanged by this fix - it only corrects *which* candidates count as "new," not the underlying polling mechanism.

## Customer ready-for-pickup notification: identified as a gap (scoped below)

**Context:** Completing an order as a shopper (`OrderCompletionScreen`, sets `status: 'ready_for_pickup'`) produces no visible signal anywhere on the customer side. Auditing confirmed why: `OrderDetailScreen`'s only poll is gated `if (order?.status !== 'shopping') return` - it was scoped tight to the one window a substitution proposal could appear in (see "Phase 4 core loop" above), so it stops the instant the order leaves `'shopping'`, before `ready_for_pickup` is ever reached. Neither `OrderDetailScreen` nor `OrdersScreen` uses `useFocusEffect` or any other refresh trigger - both load once on mount. There is no push notification library anywhere in the project (`expo-notifications`, `@react-native-firebase`, `notifee`, etc. - none present), and unlike the shopper side, `MainStack` (the customer navigator) has no context/provider wrapping it the way `ShopperAssignmentProvider` wraps `ShopperStack` - so there's also no mechanism today that could notify a customer regardless of which screen they're on.

**Findings from auditing the existing code:** `getOrdersByCustomerId()` (`orderService.ts`) fetches up to 50 orders for a customer, newest first, with no status filter - a poll would need to filter client-side or the function would need a new param. `UrgentOrderToast` (the shopper-side equivalent) isn't reusable as-is - its message and props are hardcoded to the "new order arrived" wording - a near-duplicate customer-side component would be needed. Separately, digging into `ArrivalNotificationCard`/`arrivalService.ts` for this audit surfaced a second, unrelated gap the user identified from direct experience with production curbside-pickup apps (Amazon/Whole Foods-style): `CustomerArrival` (the "I've Arrived" record) is entirely per-order - `orderID`-scoped in both the schema (`types/index.ts`) and every `arrivalService` function (`getActiveArrivalForOrder(orderID)`, `getArrivalsForOrder(orderID)`, `recordArrival({ orderID, customerID, ... })`). There is no concept anywhere in this app of "this customer's ready orders" as a group. Production apps in this space combine a customer's multiple ready orders into a single pickup handoff; this app currently has zero data model or UI support for that - every order is an independent pickup event.

**Decision:** Not yet built. Documented as three separable pieces, only the first of which was originally scoped:

1. **Ready-for-pickup notification (original ask).** New `CustomerOrderContext` (`src/context/`), mirroring `ShopperAssignmentContext`'s proven pattern almost exactly: same 8s poll interval, mounted wrapping `MainStack.Navigator` in `AppNavigator.tsx` (currently unwrapped), polling `getOrdersByCustomerId` (extended with an optional `statuses` filter to avoid re-fetching terminal orders every tick). Tracks a ref snapshot of `{orderId: status}` from the previous poll (generalizing `ShopperAssignmentContext`'s single-order ref into a map, since a customer isn't limited to one order in flight); a transition into `ready_for_pickup` fires a new `OrderReadyToast` component (near-duplicate of `UrgentOrderToast`, same `Snackbar` pattern). First poll after mount only establishes the baseline silently - same tradeoff already accepted on the shopper side (see "Rush-order interrupt" above): a customer reopening the app to an order that's been ready for a while won't get a stale "just now" toast. Also needs `OrderDetailScreen`'s poll condition widened so a customer already looking at that exact order's screen catches the transition live instead of staying frozen on `'shopping'`.

2. **Multi-order consolidation into a single pickup.** Flagged by the user as a real shortcoming they've personally hit in production pickup apps: when a customer has more than one order ready, the real system combines them into one pickup instead of treating each as independent. This app has no infrastructure for that today (see findings above - `CustomerArrival` is strictly per-order). Building it for real needs a way to group a customer's ready orders (query by `customerID` + `status: ready_for_pickup`), an "I've Arrived" flow that represents the whole group rather than one order, and a staff/shopper-facing view of everything bundled into one arrival - there's no dedicated staff role in this app currently, so that last piece needs its own design pass. Materially bigger than #1 and #3 - noted as a known gap, not scoped for implementation yet.

3. **Warn before "I'm on the way" if other orders aren't finished.** A concrete, reported failure mode independent of #2: a customer with multiple orders placed (in different time slots or not) taps "I've Arrived" while a later order is still `pending`/`assigned`/`shopping`, and ends up picking up an incomplete set. Unlike #2, this doesn't require solving consolidation - it's a pre-flight check in front of the *existing* per-order arrival flow. Before `ArrivalNotificationCard.handleArrived()` fires, check the customer's other orders (via the same `getOrdersByCustomerId` call #1 already needs) for anything still non-terminal, and if found, surface a confirmation ("You still have another order being shopped - notify staff now anyway?") instead of silently proceeding.

**Why documented before implemented:** Same reasoning as the original rush-order interrupt gap entry above - this touches multiple screens and services, and #2 vs. #3 represent genuinely different scopes of effort (a real data-model feature vs. a guard clause) that deserve an explicit decision on which to build now, rather than being bundled silently into "add a notification."

**Consequences / left open:** #3 is a real mitigation for the reported failure mode but not a full fix - a customer can still dismiss the warning and pick up a partial order on purpose (rush, mistake, whatever), and the store still has no single combined pickup to hand over even when the customer does wait. #2 is the actual production-matching behavior but is a separate, larger initiative (data model + at least two roles' UI) and stays out of scope until explicitly picked up. Like everything else in this app's notification story, #1 remains foreground-only - no OS-level push exists or is scoped here.

## Proximity-based arrival notification: two options weighed, neither built yet

**Context:** Real-world observation of a competitor's pickup app (customer-facing ETA jumping between 2-3 minutes and back, with the customer sometimes still half a mile out) raised the question of whether this app's "I've arrived" flow (`CustomerArrival`/`arrivalService.ts`/`ArrivalNotificationCard`) should auto-detect proximity instead of relying purely on a manual button tap, and whether a free-text `parkingSpot` field is precise enough when several other grocery chains' pickup lots are nearby.

**Two options considered, not mutually exclusive but very different in cost:**

1. **Structured parking-spot selection.** Replace the existing free-text `parkingSpot` string (`src/types/index.ts:202,220`, entered manually in `ArrivalNotificationCard.tsx`) with a tap-to-select spot from a small fixed set (numbered/lettered stalls), stored as an enum or small lookup table. Builds directly on the existing manual "I've Arrived" flow - no new permissions, no location code, no background processing, no app-store review exposure.

2. **Geofenced auto-notify under ~0.1 mi.** Would require live customer GPS, which this app has none of today - no `expo-location`/`react-native-geolocation-service` dependency, no lat/lng fields on any collection, and the Info.plist `NSLocationWhenInUseUsageDescription` entry is unused RN template boilerplate. Full scope: a geolocation library; foreground *and* background location permissions (background triggers separate App Store / Play Store review scrutiny); native OS geofencing (`CLCircularRegion` / Android `GeofencingClient`) rather than raw polling, for battery reasons; a custom polygon geofence matching the actual lot boundary rather than a simple radius, since a circle risks bleeding into the three nearby competing pickup lots; debounce/hysteresis on boundary crossing to avoid flapping; and explicit customer consent UX. Flagged risk: consumer GPS accuracy in a multi-building retail lot is commonly 30-100+ ft, which is a meaningful fraction of a 528 ft (0.1 mi) threshold - the same accuracy problem is the likely cause of the jumpy ETA behavior that prompted this discussion in the first place.

**Decision:** Neither built. If pursued, option 1 first (small, reuses existing infrastructure) with option 2 treated as a separate, larger initiative gated on whether the manual flow proves insufficient in practice - and prototyped against real GPS accuracy in the actual lot before committing to a 0.1 mi threshold specifically.

**Consequences / left open:** This app has no background-process or realtime-push infrastructure at all yet (see "Pull-based data, not realtime" above), which option 2 would also need to build on top of, independent of the location work itself.

## Phase 4 finished: Drop Offs, Customer Check-ins, Shopper Settings

**Context:** The last unchecked line in Phase 4 - three shopper screens (`DropOffsScreen`, `CustomerCheckInsScreen`, `ShopperSettingsScreen`) existed only as placeholders, already wired into `ShopperStack` with working nav shortcuts and count badges on the dashboard, but rendering static filler.

**Decision, in four parts:**

1. **Customer Check-ins is store-wide, not scoped to the shopper's own orders.** `CustomerArrival` has no shopper field at all, and `arrivalService.ts`'s own docstring already described the intended flow as generic "STAFF" - any on-duty shopper sees every waiting customer, matching how a real curbside desk works. New `getActiveArrivals()`/`getActiveArrivalsCount()` in `arrivalService.ts`.

2. **Drop Offs needed a real intermediate order status.** Delivery orders previously jumped straight from `shopping` to `completed` (`OrderCompletionScreen`'s own header comment: "no separate DeliveryConfirmation screen") - there was no "out for delivery, not yet dropped off" state for a Drop Offs screen to list. Added `out_for_delivery` to the `Order.status` enum (same live Appwrite REST widen as the earlier `ready_for_pickup` addition), `OrderCompletionScreen` now lands delivery orders there instead of `completed`, and `DropOffsScreen` gives the shopper a real "Mark Delivered" action (`getOutForDeliveryOrdersByShopperId`/`getOutForDeliveryCount`, new in `orderService.ts`) that finally reaches `completed`. `OrderStatusBadge` and `OrderTimeline` (customer-facing) updated for the new status - `OrderTimeline`'s status sequence is now branched by fulfillment type instead of one fixed 5-step array, incidentally fixing a pre-existing inconsistency where a delivery order's timeline always showed an unreachable "Ready for Pickup" step.

3. **Customer Check-ins closes a real, pre-existing gap: nothing ever completed a pickup order.** Auditing turned up that no code anywhere transitioned a pickup order from `ready_for_pickup` to `completed`, despite `arrivalService.ts`'s docstring describing that as step 9 of the flow. `completeOrder()` already accepted `'completed'` as a value - it just needed a caller. Customer Check-ins' "Hand Off Order" action is that caller: it marks the arrival `completed` (`updateArrivalStatus`) and the order `completed` (`completeOrder`) together.

4. **A real, severe pre-existing bug found and fixed while testing this live: `CustomerArrivals` schema drift blocked the entire arrival flow.** The live collection's actual fields (`arrivedAt`, `notifiedShopperAt`, both required datetimes; `parkingSpot`, a required integer ranged 1-5) didn't match what `arrivalService.ts`/`types/index.ts` had assumed (`arrivalTime`; `parkingSpot` as an optional free-text string) - the customer-side "I've Arrived" button failed outright (`AppwriteException: Invalid document structure`) until this was fixed. Same resolution direction as the original "Appwrite schema drift" entry above: the code was changed to match the live schema, not the other way around. `vehicleDescription`/`notes` (already in the TS type, never on the live schema) were added as new optional string attributes via the API key rather than dropped, since the UI already collected them. `parkingSpot`'s 1-5 range was only discovered by an actual failed write (`"Value must be a valid range between 1 and 5"`) - `recordArrival()` now best-effort-extracts a digit from the free-text input and clamps it into range (defaulting to 1), while preserving the original free text verbatim in `notes` so nothing the customer typed is lost. `CustomerCheckInsScreen` displays `notes`, not the now-synthetic `parkingSpot` number, for that reason.

**Why the parking-spot UI wasn't redesigned to match the 1-5 range properly:** That's exactly the "structured parking-spot selection" option already discussed and deliberately left unbuilt in the "Proximity-based arrival notification" entry above (a tap-to-select numbered stall, replacing the free-text field). Doing that now would mean making that call unprompted as a side effect of a schema-compatibility fix, not as its own considered decision - the clamp is the smallest change that makes the existing field honest against the real schema without redesigning it.

**Verified end-to-end (2026-08-31, dual-emulator):** placed a delivery and a pickup order live; claimed and shopped both; delivery order confirmed reaching `out_for_delivery` then `completed` via Drop Offs' "Mark Delivered" (both status transitions confirmed via direct Appwrite REST reads); pickup order's customer "I've Arrived" (initially failing with the schema-drift error above, confirmed fixed) surfaced correctly in Customer Check-ins with the right wait-time badge, and "Hand Off Order" confirmed completing both the arrival and the order via REST. Shopper Settings' dark/light/system toggle confirmed re-theming the whole app instantly and surviving a full app restart (`ThemeContext`'s existing persistence, simply never surfaced in any settings UI before now).

**Consequences / left open:** The parking-spot field is still free text on a schema that only meaningfully supports 5 fixed stalls - functionally fine (nothing breaks, nothing is lost), but the structured-picker redesign this points at remains its own future decision, unchanged from the entry above. Shopper Settings intentionally excludes notification preferences (no push infrastructure exists anywhere in this app) and an availability schedule (a distinct, larger scheduling feature) - both were on the original placeholder's planned-features comment but neither has real infrastructure to back it yet.

## Rush badge visibility, and proactive assignment for every order

**Context:** Two follow-on gaps surfaced after rush orders and their interrupt logic went live. First, a rush order carried no visible signal anywhere in the shopper UI - `priority: 1` existed on the document, `handleRushOrderPlacement` acted on it, but nothing on `CurrentTaskCard`, `AvailableTasksScreen`, or `TaskDetailScreen` ever displayed it, so a shopper had no way to *see* that an order was rush short of noticing it got assigned unusually fast. Second, and more structural: normal (non-rush) orders were still only ever assigned to a shopper when *that shopper* toggled Available - `handleRushOrderPlacement` proactively pushed a rush order to an idle shopper the moment it was placed, but a normal order placed while a shopper was already sitting idle-Available just sat in the pending queue, invisible, until someone's availability happened to change again (the exact gap named in "Auto-assignment via sort order" at the top of this log).

**Decision, in two parts:**

1. **Rush badge UI.** Added a shared "Rush" badge (warning-colored, `run-fast` icon) to `CurrentTaskCard`, `AvailableTasksScreen`'s task rows, and `TaskDetailScreen`, all driven by the same `order.priority === 1` check already used everywhere else. `TaskCardData` gained an `isRush: boolean` field so `ShopperDashboardScreen`'s mapping only has to compute it once. Accessibility labels on `AvailableTasksScreen` append ", rush order" when applicable, since the badge itself is icon+color only.

2. **Proactive assignment for all orders.** `handleRushOrderPlacement`'s idle-handoff step (try `getNextAvailableShopper`, assign, update `ShopperStatus.currentOrderId`) was extracted into a new shared `tryAssignToIdleShopper()` in `shopperStatusService.ts`. A new `handleNewOrderPlacement()` calls it for every order regardless of `priority`, and `CheckoutScreen` now calls one or the other after every successful order creation (previously the idle-handoff/interrupt call was gated to `priority === 1` only). Deliberately asymmetric: rush orders still fall through to `getInterruptCandidateShopper()` when nobody's idle (bumping a busy shopper); normal orders only take the idle handoff and otherwise fall back to sitting in the pending queue exactly as before - interrupting a busy shopper for a non-urgent order was never part of the ask.

**Why this needed a new notification path, not just reusing the existing one:** `ShopperDashboardScreen` already showed `NewAssignmentModal` synchronously when toggling to Available caused an auto-assignment - that path only fires from inside `handleStatusChange`, so it can't catch an order landing on a shopper who is already idle-Available and sitting on some other screen (a rush push, or now, any normal order under this change). `ShopperAssignmentContext`'s existing 8s poll (built for the rush-interrupt and urgent-order-toast features) was extended to also watch for `previousOrderId` being empty and `currentOrderId` newly set, and show the same `NewAssignmentModal` globally when that happens. A new `acknowledgeOwnAssignment(orderId)` lets the dashboard's own instant path mark that transition as "already handled" so the poll doesn't pop a duplicate ~8s later for the same order; a new `assignmentResolvedSignal` counter lets the dashboard refetch its status/current-task display when the *context's* modal (not its own) is accepted or declined while the shopper never navigated away (no focus event to trigger the usual `useFocusEffect` refresh).

**Why extend the existing poll instead of a dedicated one:** Same reasoning already established for the urgent-order toast - one provider, already polling this shopper's status every 8 seconds for a different reason, gains one more comparison on data it's already fetching, rather than a second independent poll loop running in parallel against the same endpoint.

**Consequences / left open:** This closes the "orders don't get pushed to an idle shopper unless they just changed status" gap from the original auto-assignment decision, but only for the idle-handoff case - if literally every shopper is busy when a normal order is placed, it still just sits pending with no interrupt fallback, unchanged from before. The up-to-8-second poll latency for the async notification path (vs. instant for the toggle-triggered one) is the same tradeoff already accepted for rush interrupts and the urgent-order toast. Not yet reflected in the README roadmap's Phase 5 framing ("auto-assignment serverless function" is still listed as the only planned change there) - worth a pass to reconcile since the client-side mechanism just grew materially without a backend function.

## Realtime migration: the 8s-polling era ends, verified empirically

**Context:** "Pull-based data, not realtime" (above) deferred Appwrite Realtime as a distinct follow-up phase; two later entries ("Rush-order interrupt..." and "Rush badge visibility...") investigated it again and set it aside a second time, citing "unverified territory" - specifically an unguarded `window.setInterval` call in the installed SDK's Realtime heartbeat, and an assumed-undocumented channel-string format. Carrying the same caveat forward a third time without ever actually testing it would have made "unverified" a permanent excuse rather than a real blocker, so this pass ran the empirical spike instead of reasoning about it in the abstract.

**Spike (Phase 0), and its actual result:** A throwaway `__DEV__`-gated subscribe-and-log was mounted once in `App.tsx` for 60+ seconds across both emulators in the dual-emulator setup, spanning several heartbeat cycles (the SDK's heartbeat fires every 20s) and a background/foreground cycle. Findings:
- `window` and `window.setInterval` both exist and work correctly in this RN version - the heartbeat never threw, no reconnect-loop symptom appeared. The feared crash never materialized.
- `window.localStorage` genuinely doesn't exist in this RN runtime, exactly as suspected - but the one code path that touches it (`handleResponseConnected`'s cookie-fallback session lookup) is wrapped in a try/catch that only logs and continues. This surfaces as a **known, harmless, dev-only console warning** ("Failed to parse cookie fallback: TypeError...") visible as a LogBox toast on every fresh Realtime connection in `__DEV__` builds - cosmetic noise, not a functional bug, and irrelevant to production builds where LogBox doesn't render. Left as-is rather than papering over it with a suppression, since suppressing by message-substring risks hiding a real future error that happens to match.
- The channel format `databases.{databaseId}.collections.{collectionId}.documents` (the "legacy" naming this project's `.env` collection IDs already use) works exactly as expected against this Appwrite Cloud project - confirmed receiving `create`/`update`/`delete` events within 1-4 seconds, repeatably, across a cold app launch, a background/foreground cycle, and cross-device (one emulator's write, the other's subscription). The event's own channel-list additionally showed this project's Appwrite Cloud instance now dual-emits under both the legacy `databases.../collections.../documents` naming and a newer `tablesdb.../tables.../rows` naming for the same event - useful to know if a future SDK upgrade ever deprecates the legacy form, but not something this migration needed to react to today.

**Decision:** Replaced 8s `setInterval` polling with Appwrite Realtime subscriptions across all 8 call sites that had one (`ShopperAssignmentContext`, `CustomerOrderContext`, `ShoppingScreen`, `OrderDetailScreen` were true polls; `AvailableTasksScreen`, `DropOffsScreen`, `CustomerCheckInsScreen`, `ShopperDashboardScreen` were fetch-on-focus-only and gained an *additional* focus-scoped live subscription on top, not a poll-to-push swap). New `src/services/realtimeService.ts` centralizes this: one module-level `Realtime` instance (the SDK multiplexes every subscription over one shared WebSocket internally, so per-screen subscribe/unsubscribe is exactly as cheap as the `clearInterval` calls it replaces), three collection-scoped exports (`subscribeToOrders`, `subscribeToShopperStatus`, `subscribeToCustomerArrivals` - mirroring the existing service-per-collection convention rather than one generic `subscribe(collectionId)`), `isCreateEvent`/`isUpdateEvent`/`isDeleteEvent` helpers, `onRealtimeReconnect` (fires on initial connect and every reconnect), and `onAppForeground` (an `AppState` backstop for backgrounding).

**Two architectural facts that shaped every call site, worth knowing before extending this further:**
1. **No server-side query filtering.** A collection-channel subscription delivers every document's events project-wide - there's no way to subscribe to "just this customer's orders" at the channel level. Every callback filters on `event.payload` fields itself (`customerID`, `shopperID`, `$id`, `status`) before acting, the same way the old polling callers already filtered/diffed a fetched list - this just moved *where* the filtering happens, not whether it happens.
2. **No event replay on reconnect.** If the socket drops and reconnects (network blip, backgrounding), any events that occurred while disconnected are gone - there's no backfill. This is why `onRealtimeReconnect`/`onAppForeground` exist: the two always-mounted-once global contexts (`ShopperAssignmentContext`, `CustomerOrderContext`) register a reconcile-fetch (their same baseline-establishing fetch used on mount) to run again after any reconnect, closing the gap. Screen-local subscriptions (`ShoppingScreen`, `OrderDetailScreen`, the four Phase-5 screens) deliberately do **not** register for this - they mount fresh on every visit already, and `onOpen` has no matching unregister method in this SDK version, so a screen that mounts/unmounts repeatedly would leak callbacks if it registered. Their own mount-time fetch already covers their reconcile need for that visit.

**No fixed-interval fallback poll anywhere.** Every migrated call site relies on reconcile-on-reconnect/foreground (the two contexts) or its own mount-time fetch (everything else), not a "just in case" timed poll layered on top of the subscription. Given Realtime's no-replay guarantee, a poll fallback would only mask a genuinely broken subscription rather than degrade gracefully - better to let a real connectivity problem be visible (stale data until reconnect) than silently paper over it with 8s-late data that looks live but isn't.

**Verified end-to-end (2026-09-06, dual-emulator, real Appwrite Cloud writes throughout - no mocking):** ready-for-pickup toast firing within ~1-2s of a shopper-side write; all three `ShopperAssignmentContext` signals (idle-shopper new-assignment modal, rush interrupt modal, urgent-order toast) firing live off direct database writes with no shopper-side navigation; the full substitution round trip (shopper proposes -> customer's `OrderDetailScreen` shows it live -> customer taps Approve -> shopper's `ShoppingScreen`, sitting idle on the same screen the whole time, updates to "Substitute approved" with zero polling and zero navigation on either device); a new pending order appearing live in `AvailableTasksScreen` with the screen already open. One test-methodology trap worth flagging for future live-testing sessions: after a subscription's gating condition becomes false (e.g., `ShoppingScreen`'s `hasPending` flipping false once a substitution resolves), the subscription tears itself down by design - a subsequent external write made without the screen re-arming (a fresh mount/reload) will silently not be observed, which looks identical to a broken subscription unless you know to check whether the gate re-opened first.

**Consequences / left open:** The empirical result supersedes the "unverified territory" language in the two prior decision entries - Realtime is no longer a deferred/investigated-and-set-aside item, it's implemented and load-bearing for every real-time feature in the app. The README's Phase 5 roadmap line ("Appwrite Realtime subscriptions (currently 8s polling instead)") is now stale and should be updated in a follow-up pass - deliberately not done as part of this change, since it wasn't asked for here.

## CustomerArrivals status enum drift - the same class of bug, found by re-auditing schema against live truth

**Context:** Picking this project back up for an interview/portfolio pass, the plan was to resolve the long-flagged `CustomerArrivals` structural schema mismatch (`arrivalTime` vs `arrivedAt`, `parkingSpot` string vs integer, missing `notifiedShopperAt`/`vehicleDescription`/`notes`) - the same gap named in "Appwrite schema drift" above. Re-auditing the live code first (rather than trusting an old note about what was still broken) found that mismatch had, in fact, already been fixed and shipped in commit `02046b7` ("Complete Phase 4 shopper fulfillment: Drop Offs, Check-ins, Settings") and was already documented under that Phase 4 entry above - stale notes had just outlived the fix. Re-verifying the *current* live schema directly via the REST endpoint (`GET /v1/databases/{db}/collections/{customerArrivalsCollectionId}`, same technique as the original schema-drift diagnosis) rather than trusting either the old notes or the already-fixed code turned up a second, smaller, genuinely still-live mismatch: the live `status` attribute's enum is `waiting / notified / in_progress / completed`, but `ArrivalStatus` in `types/index.ts` was typed as `'waiting' | 'acknowledged' | 'completed'` - `'acknowledged'` has never existed on the schema at all.

**Why this one never surfaced as a runtime bug (unlike the earlier casing/type mismatches, which broke on first live write):** No code path ever actually *called* `updateArrivalStatus()` with `'acknowledged'` - the only two live call sites use `'waiting'` (`ArrivalNotificationCard`, on arrival) and `'completed'` (`CustomerCheckInsScreen`'s hand-off action), both valid live values. The type was simply wider than what any caller used, so TypeScript never caught it and no write ever attempted it. A type this loose is still a real defect, though: it would have compiled and shipped a call like `updateArrivalStatus(id, 'acknowledged')` for a future staff-acknowledgment feature, which would then fail at runtime with an Appwrite enum-validation error - the exact same failure mode as the original schema-drift bug, just not yet triggered. Worth naming as a pattern: a type that's *wider* than the real schema is a latent version of the same bug as a type that's *wrong* - it just waits for a caller instead of failing immediately.

**Decision:** Narrowed `ArrivalStatus` to the live schema's actual four values (`'waiting' | 'notified' | 'in_progress' | 'completed'`) rather than to just the two currently-used values - the schema already has `notified`/`in_progress` provisioned (present since before this project touched the collection), and typing them in now costs nothing while leaving the door open for a future staff-acknowledgment step to use them without another schema-vs-code diff. Updated `arrivalService.ts`'s `updateArrivalStatus()` signature and docstring to match (previously hardcoded its own separate `'waiting' | 'acknowledged' | 'completed'` union rather than importing `ArrivalStatus`, which is how the two could silently disagree with each other as well as with the schema). Also corrected two stale doc spots found in the same pass: the README's `CustomerArrivals` schema table still showed the pre-fix shape (`orderId`/`customerId` casing, string `parkingSpot`, missing fields) even though the code had moved on, and a "Pickup Notifications" feature bullet still read "end-to-end flow still in progress" despite Customer Check-ins' hand-off action (documented above) having closed that loop weeks earlier.

**Alternatives considered:** Narrowing the type to just `'waiting' | 'completed'` (the two values actually used) was considered and rejected - it would have been the tightest possible fix, but would silently drop `notified`/`in_progress` from the type system entirely, meaning a future feature using them would need to *widen* the type again rather than just start calling `updateArrivalStatus()`. Matching the live schema's full enum now is free and avoids repeating this same diagnosis a third time later.

**Consequences / left open:** `notified` and `in_progress` are now valid in the type but still have zero writers - there's no staff-acknowledgment UI, so those two states are reachable in the schema and the type but not in practice yet. That's an intentional, named gap (not a bug) - the same "flagged, not built" treatment as the other deferred arrival-flow items above (structured parking-spot selection, multi-order pickup consolidation, pre-flight warning on incomplete order sets). Building the actual acknowledgment step is a real Phase 6 candidate if a future session wants it, but wasn't in scope for this pass.

## What Jest is, why it matters, and why this project's one test currently fails (a from-zero primer)

**Context:** This project has never had a working automated test suite - the single test file, `__tests__/App.test.tsx`, is the default React Native CLI template test, untouched since the very first commit, and it currently fails to even *run* (not "fails an assertion" - the test process itself crashes before reaching any assertion). Since this project is explicitly being documented for a portfolio/interview audience, and testing is a topic that's reasonable to be asked about directly even though this codebase doesn't demonstrate it well yet, this entry is written differently from the others above: as a plain-language primer for someone who has never used Jest, or any automated testing tool, in any language - not just a changelog of a decision.

**What "testing" means here, concretely:** Every verification described elsewhere in this log up to now - "verified live in the dual-emulator setup," "confirmed via direct Appwrite REST query," "placed a rush order, confirmed `priority: 1`" - was a *human* driving the app by hand and checking the result with their own eyes. That's real testing, and it's exactly how this project has caught most of its bugs (the schema-drift entries above are a direct product of that manual process). Automated testing is the same idea - "does the code actually do what I expect?" - but the checking is written as code itself, so a machine can run it in milliseconds instead of a person spending minutes rebooting an emulator and tapping through a flow.

**What Jest specifically is:** Jest is a *test runner* - a program that finds files matching a pattern (here, anything under `__tests__/` or named `*.test.ts(x)`), executes the code inside them, and reports pass/fail. It's the de facto standard for JavaScript/TypeScript projects, and ships pre-configured with the React Native CLI template this project started from (see `jest.config.js`, `package.json`'s `"test": "jest"` script) - it didn't need to be added, it's just never been *used*. Inside a test file, Jest provides two building blocks: `test('description', () => { ... })` (or the identical alias `it(...)`) declares one check, and `expect(actualValue).toBe(expectedValue)` (or `.toEqual()`, `.toThrow()`, and dozens of other matchers) is the actual assertion - the line that fails loudly if the code didn't do what was expected.

**Why bother, when manual testing already works?** A few concrete reasons, specific to a project like this one:
1. **Speed and repetition.** The dual-emulator verification sessions documented throughout this log take real setup time (booting two AVDs, signing into test accounts, timing a live interaction across two devices) - each one is valuable but expensive to repeat. A test that pins down, say, `getRushReadyTime()`'s 30-minute math or `recordArrival()`'s parking-spot clamping (both pure, self-contained logic already in this codebase) runs in milliseconds and can be re-run on every single code change, forever, for free.
2. **Regression safety.** `docs/DECISIONS.md` already documents several bugs that were *reintroductions* or near-misses caught only by manual re-testing (e.g. the urgent-order toast firing for orders already in the queue). A test suite's real value isn't catching the bug the first time - it's making sure a fix, once made, can never silently break again without a red test flagging it immediately, instead of waiting for the next manual pass to notice.
3. **It catches a different class of bug than TypeScript does.** `tsc --noEmit` (used throughout this project) verifies *shapes* - that a function's inputs and outputs match their declared types. It says nothing about whether the *logic* is right - `getRushReadyTime()` could return a time 30 hours in the future instead of 30 minutes and TypeScript would never notice, because the return type is just `string` either way. Only a test (or a human) that checks the actual *value* catches that.
4. **Tests double as living documentation.** A test named `'clamps parkingSpot above 5 down to 5'` states an intended behavior in a way a future reader (including a future session of this same AI-assisted workflow) can trust is still true, because it's re-verified every run - unlike a code comment, which can silently go stale.

**Why `App.test.tsx` fails today, as a concrete worked example:** Running `npx jest` throws `[@RNC/AsyncStorage]: NativeModule: AsyncStorage is null` before any test logic even executes. The test renders the real `<App />` component tree, which (via `ThemeContext.tsx`) imports `@react-native-async-storage/async-storage` - a *native* module, meaning its real implementation is Java/Kotlin and Swift/Objective-C code that only exists once compiled into an actual Android or iOS app. Jest runs in plain Node.js, with no emulator or native runtime underneath it, so the real `AsyncStorage` module has nothing to load - it's `null`, and the import throws the moment `App.tsx` requires it. This is an extremely common first-timer trap, not a bug specific to this codebase: any RN project that touches a native module in code a test imports needs that module *mocked* (a fake, JS-only stand-in that behaves like the real thing well enough for the test's purposes) before the test can run at all. React Native's Jest preset (already configured here) mocks most core native modules automatically, but third-party ones like AsyncStorage need one line of explicit setup (a `jest.config.js` `setupFiles` entry pointing at the mock AsyncStorage ships with itself) that this project's `jest.config.js` never added.

**Consequences / left open:** No tests were added or fixed as part of this entry - this was a documentation pass, not an implementation one, per what was asked. If a future session wants this project's testing story to actually demonstrate something (worth having before an interview, if testing comes up as a topic), the natural entry points, roughly in order of effort: (1) wire up the AsyncStorage mock so the existing boilerplate test at least runs, (2) write a handful of pure-logic unit tests against functions that need no mocking at all - `getAvailableTimeSlots()`/`getRushReadyTime()` in `orderService.ts` and the `parkingSpot` clamping logic in `arrivalService.ts`'s `recordArrival()` are both good first candidates, being deterministic and already isolated from Appwrite, and (3), further out, component tests for something like `RushOrderToggle` or `TimeSlotSelector` using React Native Testing Library (not yet installed) to verify rendering/interaction without a full emulator. None of this is started - named here as a clearly-scoped Phase 6 candidate, same treatment as the other deferred items in this log.

## Auto-assignment as a serverless function: what it is, what's here today, and what actually needs to change (a primer)

**Context:** The very first entry in this log ("Auto-assignment via sort order, not a routing algorithm") flagged that "a serverless Appwrite Function that runs assignment logic server-side... was considered but deferred," and the README's Phase 6 roadmap still lists it as open work. Picking it up now, written the same way the Jest primer above was: as a plain-language explanation for someone who hasn't worked with this concept before, not just a changelog line - because the honest answer to "what changes" requires first being precise about what "client-side" concretely means in this codebase today, and that it's not a stylistic simplification but a real gap.

**What "client-side" concretely means here today:** every piece of the assignment "brain" - the code that decides which order goes to which shopper - lives in `src/services/shopperStatusService.ts` (plus two query functions in `orderService.ts`) and runs on whichever device happens to trigger it. There is no third machine involved anywhere in this flow:
- `getNextOrderForAssignment()` (`orderService.ts`) and `getNextAvailableShopper()` are the two queries everything else is built from - "what's the single most time-urgent unassigned order" and "who's the longest-idle available shopper."
- `handleNewOrderPlacement`/`handleRushOrderPlacement` run on the **customer's own phone** - fired as a fire-and-forget call right after `CheckoutScreen` creates a new order. The customer's device queries for an idle shopper (or, for a rush order, an interruptible busy one) and writes the assignment directly.
- `updateShopperAvailability`, `autoAssignNextOrderTo`, `reassignIfMostUrgent`, `swapCurrentOrder`, and `getInterruptCandidateShopper` all run on the **shopper's own phone** - triggered by toggling availability, completing an order, or swapping tasks.
- "Client-side" doesn't mean "the logic is simple" - it means literally: the deciding code executes inside the React Native app process on a customer's or a shopper's own device, writing to the `Orders`/`ShopperStatus` collections using that person's own login session, with no separate authority checking the result.

**What a serverless function (an Appwrite Function) actually is:** a small piece of backend code - most commonly Node.js here, since `node-appwrite` is already a dependency - that gets uploaded once, and Appwrite's own infrastructure runs it for you on demand, not on any user's device. "Serverless" doesn't mean there's no server; it means nobody on this project has to provision or babysit one - Appwrite spins up a short-lived container to execute the function each time it's triggered, then tears it down. Two ways to trigger one:
- **Event-triggered:** the function subscribes to something happening in the database (e.g. "a document was created in the `orders` collection") and Appwrite invokes it automatically - no client is involved in the trigger at all.
- **HTTP-triggered:** a client calls it directly (the SDK's `functions.createExecution(...)`, similar to a normal network request), and the function runs and can hand back a result.

The property that actually matters for this project: a Function can run under its **own** elevated credentials (an API key, the same mechanism already used for this project's admin/debug scripts), separate from and stronger than whatever the calling user's own session is allowed to do. That's the one thing today's design has no equivalent of anywhere.

**Why this is a real problem, not just "less realistic" - two concrete issues, found in this codebase, not hypothetical:**

1. **The permission model has no gate on the writes that matter.** Every collection involved here is set to `Any: Create/Read/Update` (see the README's collection tables) - there is no narrower rule anywhere saying "only a shopper can write their own `ShopperStatus.isAvailable`" or "only the system gets to write `ShopperStatus.currentOrderId`/`Order.shopperID`." Concretely: the code that decides "this customer's order → shopper X" runs *inside the customer's own app*, using the customer's own session, and that session has exactly as much write authority over a total stranger's `ShopperStatus` document as the shopper themself does. Appwrite has no way to distinguish "the app's real assignment logic wrote this" from "a client crafted this exact same request by hand" - both walk through the identical open door, because there is only one door.
2. **Read-then-write assignment has no atomicity, so two devices can race.** Every assignment path here is two separate round trips - query for a candidate, then a separate `updateDocument` call to claim it - not one atomic "claim only if still free" operation. Two concrete races this allows, neither of which the code checks for: (a) two orders placed in quick succession can both read the *same* idle shopper as their top candidate before either write lands, then both assign that shopper - the second `updateDocument` silently overwrites `currentOrderId`, so the shopper ends up on the newer order while the first order still shows a real `shopperID`/`autoAssigned: true` even though nobody is actually coming for it; (b) the mirror case - two shoppers going Available in the same short window can both read the same single pending order as "next" and both attempt to claim it, and whichever write lands second silently overwrites `Order.shopperID`, leaving the first shopper's `ShopperStatus.currentOrderId` pointing at an order that's already moved on to someone else. Neither race has been *observed* yet - the dual-emulator sessions have never happened to land inside the timing window - but that's exactly what makes it a real, waiting bug rather than a false alarm: it gets more likely, not less, the day this app has genuinely concurrent shoppers instead of one person driving both test devices by hand.

**What moving this into an Appwrite Function is intended to change:** the decision logic (`getNextOrderForAssignment`, `getNextAvailableShopper`, `getInterruptCandidateShopper`, and the assignment writes currently spread across `assignOrderToShopper`/`unassignOrder`/`interruptOrder` in both service files) relocates into one Function, running under its own API key rather than any caller's session. `Orders`/`ShopperStatus` permissions then get tightened so a normal client session can no longer directly write the fields that decide assignment (`shopperID`, `currentOrderId`, `autoAssigned`) - only the Function's key can. The client still creates orders and still flips its own `isAvailable`; it stops being the thing that decides *who gets what*. This closes both problems above together: one server-side execution per trigger removes the "two clients race to claim the same thing" class of bug (there's still concurrency to reason about if Appwrite ever ran two executions of the same trigger simultaneously, but that's one place to get right instead of ten call sites spread across two files), and the tightened permissions mean a client can no longer forge an assignment at all - only the Function's own key is allowed to write those fields.

**Open design question, deliberately not decided here - event-triggered vs. HTTP-triggered:** this is a real fork, not a detail, and changes what implementation actually looks like:
- *Event-triggered* (the function subscribes to `orders.*.create` and `shopperStatus.*.update`) removes the client from the trigger entirely - `CheckoutScreen` would just create the order and stop calling `handleNewOrderPlacement`/`handleRushOrderPlacement` itself; `updateShopperAvailability` would shrink to just writing `isAvailable`. Closer to how a real production system would do this, and it's one more place client code stops deciding backend state - but it means two separate event subscriptions/code paths to configure and reason about, and less direct control over exactly when assignment runs relative to the rest of checkout.
- *HTTP-triggered* (the client calls `functions.createExecution(...)` at the exact spots that currently do direct `databases.*` calls) keeps today's call sites structurally the same, just swapping what's inside them - easier to stand up and debug one step at a time - at the cost of the client still being the thing that decides *when* assignment happens, even after it stops deciding *how*.

**Consequences / left open:**
- Checked directly against this project's live Appwrite Cloud instance: the existing dev API key (the same one used for admin/debug scripts, see "Appwrite schema drift" above) does **not** currently have Functions scope - a direct REST call against `/functions` returned `401 missing scopes (["functions.read"])`. Standing up a Function will need that key's scopes widened in the Appwrite console, or the Appwrite CLI installed and logged in interactively - both require the project owner's own Appwrite account access and can't be done unattended from here.
- No Appwrite CLI is installed in this environment, and there's no `appwrite.json` or `functions/` directory in the repo yet - both need to be created as part of implementation, not present today.
- Tightening `Orders`/`ShopperStatus` permissions has to be audited against every *other* legitimate client write to those collections first (a shopper's own `isAvailable` toggle, `pickedItems` updates mid-shop, etc.) - narrowing too broadly would break real features that have nothing to do with assignment. Not done as part of this entry; it's the first real step before any permission change ships, not something to do casually alongside the Function itself.
- Nothing is implemented yet. This entry documents the plan and the concrete problems motivating it, the same way the rush-order interrupt feature and the Realtime migration were both written up before/alongside implementation rather than only after the fact.

## Auto-assignment Function: built, deployed, and verified live (event-triggered, chosen over HTTP-triggered)

**Context:** Direct follow-up to the primer above. Event-triggered was chosen over HTTP-triggered - it removes the client from the trigger entirely, which was the more compelling property of the two once weighed against the extra setup cost. This entry covers what got built (`functions/auto-assignment/`), the two real bugs hit standing it up, and what's been verified live against the actual Appwrite Cloud project versus what's still just reasoned-through.

**What got built:** one Appwrite Function (`functions/auto-assignment/src/main.js`, Node.js), registered for three events - `orders` create, `orders` update, `shopperStatus` update - covering every entry point the client-side version had. Each handler is named to match its client-side predecessor one-for-one (`handleNewOrderPlacement`, `handleOrderReleased`, `handleShopperBecameAvailable`, `handleShopperWentUnavailable`) and reuses the same queries and field writes documented in the primer above, just relocated. No Appwrite CLI was used to deploy it - `functions/auto-assignment/scripts/deploy.js` does the same job (package the code, create/update the Function resource, upload and activate a deployment) directly through the already-installed `node-appwrite` server SDK, since the CLI isn't installed here and its login flow needs an interactive browser session this environment can't do unattended.

**Two real bugs found standing this up, neither guessable in advance - both fixed, both worth naming for next time:**
1. **The dynamic per-execution API key needs its own explicit scopes, and `databases.read`/`databases.write` aren't the ones that gate document access.** The first live test (flipping a test shopper to Available) executed successfully but failed inside with `missing scopes (["documents.read"])`, even though the function was created with `scopes: ['databases.read', 'databases.write']`. Appwrite generates a fresh, function-scoped API key for every execution (injected via the `x-appwrite-key` request header - see the code's own comment on why this is used instead of a static key baked into an env var), and that key's actual permissions are exactly the `scopes` array passed to `functions.create`/`.update` - `databases.read`/`.write` govern database/collection-level operations, not the documents inside them. Fixed by adding `documents.read`/`documents.write` to the scopes list.
2. **The event actually delivered to a Function at runtime doesn't match the naming used to register it.** `scripts/deploy.js` registers events using the legacy `databases.{db}.collections.{id}.documents.*.{action}` form (matching every other collection ID reference already in this project's `.env`), but the `x-appwrite-event` header the function receives at runtime uses the newer `tablesdb.{db}.tables.{id}.rows.*.{action}` form for the identical event - confirmed by the first test's log line reading `Ignoring event outside scope: tablesdb...` even though the shopper-status update it was reacting to was real. This is the exact same dual-naming fact the Realtime migration entry already flagged for Realtime *channels* - turns out it applies to Function *event headers* too, and registration-time naming and delivery-time naming don't have to agree. Fixed by matching on the bare collection ID as a substring (`event.includes(ORDERS_COLLECTION_ID)`) instead of a specific path shape - robust to either naming scheme, since collection IDs like `orders`/`shopperstatus` are distinctive enough not to collide with anything else in the string.

**Verified live against the real Appwrite Cloud project (2026-09-12, direct REST calls driving state changes, function execution logs read back to confirm behavior - no emulator needed for this part, since nothing client-side changed yet):**
- **Shopper becomes available, order gets auto-assigned:** flipping a test `ShopperStatus` document's `isAvailable` to `true` (with `currentOrderId` empty) produced a `shopperStatus` update event; the function picked the single most urgent pending order and assigned it - confirmed via the order's `status`/`shopperID` flipping and the function's own log line (`"Shopper ...: auto-assigned order ..."`).
- **Shopper goes unavailable while holding an order, it's released and re-checked:** flipping the same shopper back to `isAvailable: false` released their order (`shopperID: ''`, `status: 'pending'`) and cleared `ShopperStatus.currentOrderId` - both writes the function's own responsibility now, not the client's. The resulting `orders` update event correctly triggered `handleOrderReleased`, which checked whether the released order was still the single most urgent pending one and whether an idle shopper existed - at that moment neither did (the only shopper had just gone unavailable), and it correctly logged "left queued" rather than force-assigning anything.
- **New order placed while a shopper is idle, assigned immediately via the *create* event specifically:** cleared the queue, confirmed the test shopper was genuinely idle (`isAvailable: true`, `currentOrderId: ''`), then created a brand-new order directly via REST (no shopper-status change involved at all) - it was assigned within seconds, with the function's log line explicitly attributing it to the create-triggered handler, confirming this is a distinct, independently-working entry point from the shopper-status path above, not just the same one re-observed.
- **No infinite loop, across a chain of state transitions.** The full sequence above (available → assigned → unavailable → released-and-requeued → available again → re-assigned) ran to completion across several real writes with each chain terminating in one or two follow-on events, exactly as each handler's "what stops this from re-firing itself" docstring predicted - not just asserted, actually watched happen via the execution log's timestamps.

**Not yet independently verified live, reasoned-through instead:** the rush-order interrupt fallback (`getInterruptCandidateShopper`, used inside `handleNewOrderPlacement` when a rush order arrives with no idle shopper available) and `handleOrderReleased`'s *positive* path (a released order successfully hopping straight to a different idle shopper, rather than the "no idle shopper" negative path that's what actually got exercised above). Both compose the same primitives already proven correct live (`getNextAvailableShopper`, `assign`, `release`) rather than introducing new ones, so confidence is reasonably high, but "reasoned to be correct because it shares tested plumbing" and "actually watched happen" are different claims, and only the honest one is made here.

**Consequences / left open:**
- The client-side code this Function is meant to replace (`handleNewOrderPlacement`/`handleRushOrderPlacement`/`reassignIfMostUrgent`/`autoAssignNextOrderTo`/`tryAssignToIdleShopper`/`getNextAvailableShopper`/`getInterruptCandidateShopper` in `shopperStatusService.ts`, plus the calls into them from `CheckoutScreen.tsx` and `OrderCompletionScreen.tsx`) is **still live and unchanged** - right now both the old client-side logic and the new server-side Function are running side by side, each capable of independently racing to assign the same order. This is fine for the verification above (which drove state changes directly via REST, bypassing the app entirely) but is not a state to leave the app itself running in - removing the now-redundant client-side logic is the next required step, not an optional cleanup.
- The permission-tightening half of the original plan turned out to have a real wrinkle worth resolving before touching it: Appwrite's permission model is collection/document-level, not field-level, so "only the Function may write `shopperID`, but a shopper may still write their own `isAvailable`/`pickedItems`" can't be expressed as a single permission rule the way the primer above implied - it would need either leaving collection permissions as they are (closes the concurrency problem via the Function, but leaves the "no gate on the write" problem exactly as open as before), or routing every write to those fields through Function executions instead of direct client writes, including the manual-claim/swap flow (`swapCurrentOrder`, `TaskDetailScreen`) which the auto-assignment work above deliberately left alone as a distinct, human-decided action rather than "assignment." Neither option was chosen yet - flagged here rather than decided unilaterally, since it changes how much of the app this migration actually touches.
- Test data consequence, noted for transparency: verifying this live meant mutating real documents in the shared Appwrite Cloud project's `orders`/`shopperstatus` collections (a handful of already-stale test orders from a prior session were cancelled to get a clean queue for the create-path test, and one fresh test order was created and left in its assigned state) - all pre-existing test fixtures, not anything representing real customer data.

## Client-side assignment logic removed - the Function is now the only path, scoped to auto-assignment only

**Context:** Direct follow-up to the two entries above. With the Function live-verified, the old client-side logic it replaces was still running unchanged, racing the Function on every assignment - the decision this entry covers is what got removed, and how far the accompanying permission lockdown actually went, given the field-level limitation the primer already named.

**Decision on permission scope:** scoped to auto-assignment only, not the larger write-path lockdown. Genuinely preventing a client from ever writing `shopperID`/`currentOrderId` directly would require revoking Update permission from `Orders`/`ShopperStatus` entirely (Appwrite has no field-level permissions - see the primer above) and rebuilding *every* legitimate direct write those collections currently get (`pickedItems`/`itemIssues` during shopping, `isAvailable` toggling, `clearCurrentOrder`, substitution proposal/approval, status transitions through the whole delivery/pickup lifecycle, the manual-claim/swap flow) as Function-mediated writes instead - a multi-session project of its own, not something to fold into this pass. `Orders`/`ShopperStatus` permissions are unchanged; the "no gate on the write" problem the primer named is still open, by choice, not by oversight.

**What actually got removed from the client, now that the Function is the sole path:**
- `shopperStatusService.ts`: deleted `getNextAvailableShopper`, `getInterruptCandidateShopper`, `reassignIfMostUrgent`, `autoAssignNextOrderTo`, `tryAssignToIdleShopper`, `handleNewOrderPlacement`, `handleRushOrderPlacement` outright - every one of these now has a server-side equivalent in `functions/auto-assignment/src/main.js`. `updateShopperAvailability` was cut down to just the `isAvailable` write itself (previously ~80 lines implementing both the "becoming available" and "becoming unavailable mid-order" branches inline). `assignOrderToShopper`, `clearCurrentOrder`, and `swapCurrentOrder` (manual claim/swap - a human decision, deliberately out of scope, see the permission-scope decision above) are unchanged.
- `CheckoutScreen.tsx`: the fire-and-forget `handleRushOrderPlacement`/`handleNewOrderPlacement` calls after `createOrder()` are gone - the order's own `create` event is the trigger now, nothing needs to be called.
- `OrderCompletionScreen.tsx`: the explicit `autoAssignNextOrderTo()` call (and the synchronous "Nice work! A new order has been assigned" alert built on its result) after `clearCurrentOrder()` is gone, for the same reason described next.

**The one real behavioral consequence, caught by TypeScript before it shipped, not by inspection:** `updateShopperAvailability` used to return the freshly auto-assigned order synchronously (`result.assignedOrder`), and `ShopperDashboardScreen.handleStatusChange` used that to show its own instant `NewAssignmentModal` the moment a shopper toggled Available. Once assignment moved server-side and asynchronous, there's no synchronous result left to return - removing the field from the return type (rather than leaving it always-`null`, which would have quietly broken the feature while looking unchanged) turned every read of `result.assignedOrder` into a compiler error, `npx tsc --noEmit` catching every affected call site by construction instead of by memory or grep. The fix wasn't a workaround: `ShopperAssignmentContext` already had a general realtime-driven "new assignment" detector (`checkNewAssignment`, watching for the shopper's own `currentOrderId` going from empty to set) built for the *other* case this problem already had - an order landing on an idle shopper with no toggle involved. That detector needs no changes to also cover the toggle case; the two paths and their `acknowledgeOwnAssignment` coordination handshake (needed only to stop them double-firing for the same assignment) collapse into the one that already existed. Same fix pattern applied to `OrderCompletionScreen`: its own "new order assigned" alert (also built on a synchronous result that no longer exists) was removed outright rather than reworked, since `ShopperAssignmentContext`'s modal already covers it.

**Verified live in the running app (dual-emulator, 2026-09-12), not just REST this time:** rebuilt and relaunched on both AVDs, signed in as the shopper test account. Toggling Unavailable while holding order `#9397E054` correctly released it (dashboard flipped to "No tasks assigned," the available-tasks count went 0→1) - confirmed live over the dashboard's existing realtime subscription, no manual refresh. Toggling back to Available reassigned the same order and popped `NewAssignmentModal` reading "New Order Assigned - #9397E054" - fired entirely by `ShopperAssignmentContext`'s realtime subscription, with no client-side assignment code anywhere in the call path. `npx tsc --noEmit` and `npx eslint .` both clean after the refactor (same 14 pre-existing style warnings as before, 0 errors).

**Consequences / left open:** The permission-tightening gap named in the primer is unchanged and still open - flagged, not fixed, by explicit choice. The larger write-path lockdown (routing every Orders/ShopperStatus write through Functions) remains a clearly-scoped, separate future project if full lockdown is ever wanted, not something this pass started. `functions/auto-assignment/scripts/deploy.js` is the reproducible path to redeploy the Function after any future change to `src/main.js` - no Appwrite CLI needed, same dev API key already in `.env` (now with the widened Functions/Documents scopes this work required).

## Cookie-fallback `getItem` error: the real fix, superseding "left as-is"

**Context:** The Realtime migration entry above documented the `window.localStorage`-doesn't-exist-in-RN console warning as "known, harmless... left as-is rather than papering over it with a suppression." That was the right call at the time given the options actually considered (all of them - a message-substring suppression, a `window.localStorage` polyfill - genuinely were bandaids, either hiding future unrelated errors or feeding the SDK a decoy it couldn't tell apart from the real thing). This entry replaces that decision once a *third* option was identified: fixing the actual gap in the SDK's own code, not the symptom of it.

**The actual defect, precisely:** `node_modules/appwrite`'s installed SDK (21.5.0) touches `window.localStorage` in four places. One (`prepareRequest`, cookie-fallback header on outgoing requests) and one (`Realtime.handleResponseConnected`'s cookie write-back) are already guarded with `typeof window !== 'undefined' && window.localStorage` - proof the SDK's own authors know this check is necessary in some environments. Two read sites - `Client`'s own internal `onMessage` handler for the `'connected'` event, and `Realtime.handleResponseConnected`'s session lookup (the one actually firing in this app, confirmed by the exact console.error text matching) - were missing that same guard entirely. In RN, `window` exists but `window.localStorage` doesn't, so both throw `TypeError: Cannot read property 'getItem' of undefined` on every fresh Realtime connection. Both throws happen to be caught somewhere upstream (one by `handleResponseConnected`'s own try/catch, one by a broader catch around the whole `onMessage` handler) - which is *why* this was only ever cosmetic, not a functional bug - but the gap was real either way, just accidentally non-fatal.

**Decision:** Patched the SDK directly with `patch-package`, adding the exact same guard the SDK already uses elsewhere to the two missing sites, across all three shipped builds (`dist/{esm,cjs,iife}/sdk.js` - RN/Metro resolves `dist/cjs/sdk.js` via `package.json`'s `"main"` field, since there's no `"react-native"` field and no `"module"`-first resolution here, but all three were patched for correctness regardless of which one actually loads). `patch-package` added as a dev dependency, `patches/appwrite+21.5.0.patch` committed, and `"postinstall": "patch-package"` added to `package.json` so the fix reapplies automatically after every `npm install` - verified by deleting `node_modules/appwrite` entirely, reinstalling vanilla, and confirming `patch-package` reapplied both guards correctly with no manual step.

**Why this isn't the same class of fix as the suppression/polyfill options rejected earlier:** those options left the underlying gap in place and either hid its symptom or fed the SDK fake data to stop it from noticing. This patch makes the vulnerable line never execute in an environment without `localStorage` - the exact same outcome the SDK's own author already chose for the other two touchpoints, just extended to the two they missed. Nothing is hidden; if a genuinely different error ever occurs in this exact spot, it will still surface normally, because the guard only skips the `localStorage` read itself, not the surrounding error handling.

**Verified live (2026-09-12, dual-emulator):** rebuilt with the patched SDK, relaunched the app, and drove the *exact* originally-reported scenario - Settings → Logout → confirm - end to end. `adb logcat` showed **zero** occurrences of "cookie fallback" (or `localStorage`, or any `LogBox` mention) across the whole flow, compared to it appearing on every single fresh Realtime connection before the patch (confirmed moments earlier via the same relaunch-and-check method, still throwing pre-patch). `npx tsc --noEmit` and `npx eslint .` both clean afterward (same 0 errors as before this change).

**Consequences / left open:** This is a local patch to a third-party dependency, not an upstream fix - it needs to be regenerated (`npx patch-package appwrite`) if the `appwrite` version is ever bumped, since the exact line numbers/text it targets could shift. Filing the equivalent fix upstream against the Appwrite JS SDK's own repo (`npx patch-package appwrite --create-issue` scaffolds exactly this) would let a future SDK release make the local patch unnecessary entirely - not done as part of this pass, since it wasn't asked for, but a natural next step if this project's maintainer wants to close the loop with upstream.

## Customer arrivals: a live badge and a non-blocking toast, closing a real gap in the Dashboard's realtime wiring

**Context:** Asked directly why a customer marking themselves arrived doesn't pop up a notification for the shopper "such as when an order is assigned." Investigating turned up two separate facts worth separating: one was a deliberate design choice from when Customer Check-ins was originally built (Phase 4), the other was a real, unintentional gap nobody had named until now.

**The deliberate part - why arrivals were never going to get a modal like `NewAssignmentModal`:** this app already runs two different notification patterns side by side. `NewAssignmentModal`/`OrderInterruptedModal` are for something addressed to *one specific shopper* who needs to accept/decline - a blocking popup makes sense because exactly one person needs to act. `AvailableTasksScreen`/`DropOffsScreen`/`CustomerCheckInsScreen` are a shared-queue pattern instead - a count badge plus a live list, because the underlying thing (an arrival, same as an unclaimed order) isn't addressed to anyone in particular; any on-duty shopper can act on it, matching `arrivalService.ts`'s own docstring describing the flow as generic "STAFF." A modal firing identically on every one of several active shoppers' screens for the same single arrival would be the wrong notification shape entirely, not a lesser version of the right one.

**The real gap - the Dashboard's badge itself wasn't actually live.** Checked the code directly rather than assuming: `ShopperDashboardScreen`'s `useFocusEffect` already had realtime subscriptions for `shopperStatus` and `orders` (from the earlier Realtime migration), but never one for `subscribeToCustomerArrivals` - so the "Customer Check-ins" count only ever refreshed on focus (navigating away and back). A shopper sitting on the Dashboard when a customer arrived got no signal at all, live or otherwise - not even a badge tick - which is inconsistent with how live the rest of the app already feels, and not something anyone had chosen on purpose; it just wasn't wired up when that screen was built.

**Decision:** Two additions, matching the shared-queue pattern rather than replacing it with a modal:
1. **Live badge:** added `subscribeToCustomerArrivals` to `ShopperDashboardScreen`'s existing focus-scoped subscription set, refreshing the count on every arrival create/update/delete. Deliberately *not* filtered to this shopper (unlike the `shopperStatus`/`orders` subscriptions there) - Customer Check-ins is store-wide, so every arrival matters to the count regardless of who's active.
2. **Non-blocking toast:** new `NewArrivalToast` (`src/components/shopper/NewArrivalToast.tsx`), a `Snackbar` mirroring `UrgentOrderToast`'s existing non-blocking treatment, wired into `ShopperAssignmentContext` (already the one place that watches live, app-wide, regardless of which shopper screen is open) via a new `subscribeToCustomerArrivals` handler filtered to *create* events with `status: 'waiting'` only - not the update `CustomerCheckInsScreen`'s own "Hand Off Order" action makes, since this toast means "someone just arrived," not "an arrival's status changed." Includes a "View" action (mirroring the customer-side `OrderReadyToastProps`) that navigates straight to Customer Check-ins via `useNavigation()`, newly added to this context (confirmed safe: `ShopperAssignmentProvider` is mounted inside `AppNavigator`'s `NavigationContainer`, same as the customer-side context already doing this).

**Verified live (2026-09-12, dual-emulator + direct REST writes to simulate the customer's tap, same technique as the auto-assignment work above):** with the shopper sitting on the Dashboard the whole time, no navigation - a fresh `CustomerArrival` document appearing via REST ticked the badge live (1→2→3 across three test arrivals) and popped `NewArrivalToast` reading "Rush Tester has arrived for pickup - #77247401." each time. Tapping "View" navigated correctly to Customer Check-ins, showing the live list with the right vehicle/parking-note details already present. Deleting the test arrivals afterward ticked the badge back down live, confirming the subscription isn't create-only. `npx tsc --noEmit` and `npx eslint .` both clean (0 errors, same 15 pre-existing warnings).

**Consequences / left open:** The toast fires identically for every on-duty shopper, same as the badge already did and same as `UrgentOrderToast` already does for urgent orders - not scoped to "whoever's most free," since this app has no per-shopper targeting concept for store-wide queue items and building one wasn't asked for here. If multiple shoppers are active, everyone sees the same toast for the same arrival - consistent with the existing shared-queue pattern, not a new inconsistency introduced by this change.

## Arrival hand-off corrected: a targeted modal with a timeout and reassignment, superseding the store-wide toast

**Context:** Direct correction to the entry immediately above. The store-wide toast was built on a misunderstanding of the intended design - the actual model (matching a real curbside-pickup app the user has used) is closer to order assignment than to a shared queue: an arrival is addressed to *one specific shopper* (whoever shopped the order - `Order.shopperID` is already exactly that, no new targeting concept needed), shown as a blocking modal requiring an explicit accept/decline, and if that shopper doesn't respond within a timeout, they're marked unavailable and the hand-off reassigns to the next available shopper. The live badge from the entry above is unaffected and stays - only the *notification* mechanism (toast → targeted modal) was wrong.

**Why a timeout mechanism needs a scheduled Function, not a client-side timer:** the timeout has to fire even if the addressed shopper's app is backgrounded or closed - a `setTimeout` in the React tree can't do that. `functions/auto-assignment` (already event-triggered for order/shopper-status assignment - see the two entries above) gained a fourth trigger: a `* * * * *` cron schedule (every minute - the finest granularity standard cron supports), running `handleScheduledSweep()`. The actual timeout is 60 seconds (user's choice, weighing "customer shouldn't wait long" against "a shopper mid-task needs a moment to check their phone"), so in the worst case a stale arrival is caught 60-119 seconds after crossing the timeout, not at exactly 60s - a real, named limitation of cron's 1-minute floor, not an implementation shortfall.

**Decision, in three parts:**
1. **Targeting:** `ArrivalNotificationModal` (replaces `NewArrivalToast`, deleted) is shown only to the shopper `ShopperAssignmentContext`'s `handleArrivalEvent` finds via `Order.shopperID` matching this session's own `shopperId` - checked on every `CustomerArrivals` create *or update* event (not create-only; a reassignment landing on a new shopper is an update to the same document, and needs to reach them the same way a fresh arrival does). Accept ("Hand Off Order") stamps the arrival `in_progress` and navigates to Customer Check-ins to complete the physical hand-off later; decline ("Unavailable", same label and same-shaped action as `NewAssignmentModal`'s decline) calls a new `releaseArrivalHandoff()` (orderService.ts) that clears just `Order.shopperID`, deliberately not going through `updateShopperAvailability()` - see below.
2. **Reassignment:** a new `reassignStuckArrival()` helper in the Function (shared by all three trigger origins - decline, timeout, and retry-on-later-sweep) finds the order's still-`waiting` arrival and hands it to the next idle shopper via the same `getNextAvailableShopper()` already used for order assignment, transferring `Order.shopperID` to them (the user's explicit choice - the new shopper becomes the order's shopper of record, matching how every other reassignment in this app already works).
3. **Timeout → unavailable:** `handleScheduledSweep()` finds arrivals stuck `waiting` past 60s and marks that shopper `isAvailable: false` - the resulting `shopperStatus` event reaches `handleShopperWentUnavailable` (already existing), which now also checks the shopper's `ready_for_pickup` orders for stuck arrivals to reassign, independent of whether they were also mid-shopping something else.

**Three real bugs found live-testing this, not while writing it - each fixed, not worked around:**
1. **`handleShopperWentUnavailable`'s release step had no status guard.** It unconditionally forced any `currentOrderId` order back to `status: 'pending'` - fine when that field genuinely points at a shopping-stage order, but `currentOrderId` is normally cleared the moment an order reaches `ready_for_pickup` (`OrderCompletionScreen`'s `clearCurrentOrder()`) in a *separate*, non-atomic write from `completeOrder()` itself. A crash between those two calls - or, as actually happened here, a test script forcing an order to `ready_for_pickup` via direct REST without also clearing `currentOrderId` - leaves it stale, and the old code would have silently corrupted an already-completed order back into looking like a fresh unclaimed one the moment that shopper went unavailable. Fixed by fetching the order first and only releasing if its status is still `'assigned'` or `'shopping'`; otherwise the stale pointer is cleared and the order is left untouched. Caught only because a live test happened to combine "shopper timed out" with "their `currentOrderId` was stale" - not something reading the code in isolation would have surfaced.
2. **Decline had no exclusion, so it could hand the arrival straight back to the same shopper who just declined it.** Declining deliberately doesn't mark the shopper unavailable (see below) - they can easily still be idle immediately after, which is exactly what `getNextAvailableShopper()` looks for, with no memory of who just said no. Confirmed live: rigged two shoppers' `lastActiveTimeStamp` so the decliner would be picked *first* without a fix, then verified the reassignment correctly skipped them once the fix was in. Fixed with a new `declinedByShopperID` field on `CustomerArrival` (a genuine live-schema addition, not a repurposed existing field - `interruptedAt`/`interruptReason` were considered and rejected for this, since stamping a shopperID into a field named and previously used for a human-readable interrupt reason would have been confusing for an unrelated purpose), written by a new `recordArrivalDecline()` before `releaseArrivalHandoff()` runs, read by `reassignStuckArrival()` as an exclusion, and reset to `null` once someone new is holding the arrival (deliberately remembers only the single most recent decliner, not a full history - a named scope limit, not an oversight).
3. **A stale `pendingArrival` referencing an already-deleted arrival threw a raw `AppwriteException` on accept/decline.** Surfaced by this session's own rapid REST-driven test scripts (delete-then-recreate within seconds - not a sequence a real customer produces), but a stale modal outliving its underlying document is still a real reachable state. Fixed by treating a "could not be found" failure on either action as a silent no-op (clear the modal) rather than surfacing the raw error - any other failure (network, permissions) still alerts normally.

**Verified - a mix of live UI and direct function-execution-log inspection, since RN's New Architecture routes `console.*` to React Native DevTools, not `adb logcat`, in this project's setup (worth knowing for next time - lost time this session before realizing it):**
- **Targeted modal, create path:** confirmed twice via screenshot, `ArrivalNotificationModal` showing the correct order/customer for a freshly-created arrival, on the addressed shopper's device only.
- **Live badge:** unaffected by this change, still ticking live (already verified in the entry above).
- **Decline → release without status corruption → reassignment:** confirmed via the UI (tapped "Unavailable", watched `Order.shopperID` clear via REST) and via the rigged-exclusion test described in bug #2 above.
- **Timeout → unavailable → cascade retry across multiple shoppers:** confirmed entirely via function execution logs across several real minutes of wall-clock time (not simulated) - shopper A timed out and was marked unavailable, the immediate reassignment attempt found no one free and logged "left stuck," the next two scheduled sweeps retried and still found no one, and once shopper A themselves became available again the very next sweep successfully reassigned the arrival to them - the full retry-until-someone's-free loop the design calls for, caught happening organically while this session was mid-debugging something unrelated, not engineered as a test.
- `npx tsc --noEmit` and `npx eslint .` both clean (0 errors, same 15 pre-existing warnings) after every change in this entry.

**Consequences / left open:**
- A shopper holding more than one `ready_for_pickup` order that both get arrivals close together will only ever see a modal for whichever arrived most recently - `pendingArrival` isn't a queue. Matches how `NewAssignmentModal`'s `pendingAssignment` already behaves for the same reason; not a new inconsistency.
- This session's own REST-driven test methodology (directly POSTing an order already in `ready_for_pickup` status, bypassing the real checkout→shopping→completion lifecycle) tripped the Function's *own* `orders` create-event handler (`handleNewOrderPlacement`, which assumes any newly created order is `pending`+unassigned - true for every order the real app ever creates, never true for a test script inserting one directly at `ready_for_pickup`). No idle shopper happened to exist at the moment this test order was created, so it was a near-miss rather than an observed corruption - but it means future live testing of arrival hand-off should `PATCH` an existing, normally-created order into `ready_for_pickup` rather than `POST` a new one directly in that status, to avoid re-tripping this same test-only edge.
- The `declinedByShopperID` live-schema addition was made directly via the project's dev API key (same technique as every other live schema change in this log), not through any migration tooling - there is none in this project.
